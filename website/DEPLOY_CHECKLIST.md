# Deploy Checklist

Pre-launch checklist for the TidyByte marketing site. Run through end-to-end the first time you point a real domain at the site. The site is configured for `tidybyte.yord.si`.

The site lives in `website/` of the monorepo. Run the commands below from `website/` unless a step names `ios/`.

## 0. Site architecture (Astro)

The site is an Astro static build with Tailwind + vanilla JS (no framework runtime). Ongoing CI guard: `npm run check` (asset-hash check + SEO audit + OG-card check; see `public/README.md`).

- `src/pages/` — routes as real Astro pages (`index`, `[lang]` for the 20 localized landing pages, `404`, `privacy`, `terms`, `support`, `changelog`, `mac`, `activity-monitor-alternative`, `[page]` for the 16 tool landing pages, `blog/index`, `blog/[slug]`, the `.md` alternates, plus generated `llms.txt`, `llms-full.txt`).
- `src/layouts/SiteLayout.astro` — the Astro layout every page renders through: `<head>` template (SEO/OG/article meta, LCP preloads, hreflang, Speakable + BreadcrumbList JSON-LD) and the shared chrome. The visible "Quick answer" box is placed by `src/lib/content.ts` (`withQuickAnswer`, at the `<!-- quick-answer -->` marker, or under the hero figure/header if the content file has no marker).
- `src/components/` — the site chrome (`chrome/Header.astro` with the language switcher and theme menu, `chrome/Footer.astro`) and the landing page body (`HomeMain.astro`).
- `src/components/HomeMain.astro` — the landing page as a component: hero, stats, the interactive iPhone and Mac app replicas (radio-and-CSS switchers styled by `.ios-demo` / `.mac-home-demo` in `src/input.css`), toolkit, privacy, FAQ. **This is the file you edit to change the landing page copy.** Every label in it is a translated string, so a label added without a translation in all 20 `site-translations/*.json` files fails `build-site-translations.mjs`.
- `src/content/pages/*.html` — page body content for every page other than the home page (the file you edit to change that page's copy). `index.html` here is GENERATED: it is the frontmatter-stripped snapshot of `HomeMain.astro` that the `llms.txt` / `*.md` endpoints read — never hand-edit it.
- `src/content/pages/index.<slug>.astro` — the 20 generated localized copies of `HomeMain.astro`, rendered by `[lang].astro` as components.
- The home page has no LCP image preload: its hero devices are HTML/CSS, so the LCP element is the `<h1>`. (Blog posts and `/mac` still preload their AVIF heroes.)
- `src/components/chrome/{Header,Footer}.astro` — single-source header/footer shared by all pages.
- `src/data/pages.ts` — per-page `<head>` metadata + JSON-LD (add an entry + a content file when publishing a new post).
- `src/data/tools.ts` — copy, comparison tables and FAQs for the tool landing pages. Adding a tool page means one entry here plus one `tool-<slug>.html` content file; the sitemap priority list in `astro.config.mjs` is the one thing that must be updated by hand.
- `src/lib/llms.ts` — HTML-to-Markdown used by the `llms.txt` / `.md` endpoints.
- `public/` — static assets served as-is (images, fonts, JS, robots.txt), plus Cloudflare Pages `_headers` and `_redirects`. The sitemap is generated at build time by `@astrojs/sitemap` (`sitemap-index.xml`); `llms.txt` is generated by an Astro endpoint.
- Build order: `astro build` renders `dist/` → Tailwind CLI writes `dist/assets/css/styles.css` → `hash-assets.mjs` fingerprints CSS/JS and rewrites references.
- Editing page copy: change `src/content/pages/<page>.html` — or `src/components/HomeMain.astro` for the landing page — then regenerate the localized pages (`node scripts/localization/site/build-site-translations.mjs`) and run `npm run dev` (or `build && preview`).

## 5. Deploy to Cloudflare Pages

- Confirm the existing Pages project and account before deploying; do not create a second project by assumption.
- Build and check from `website/`. Set the Pages root directory to `website`, build command to `npm run build`, output directory to `dist`, and Node version to 22.
- Deploy a preview first and verify route behavior, headers, and the support email link.
- When using Wrangler, load the existing Cloudflare credentials from the root `.env` without printing or copying the token into command arguments or logs.

## 6. Support contact

- The support page uses a `mailto:` link. Visitors choose whether to open their email app and send a message.
- No form data is collected or proxied by the Cloudflare site.

## 7. Set the custom domain

In the confirmed Cloudflare Pages project:

- Add `tidybyte.yord.si` under **Custom domains** after confirming the `yord.si` zone and checking for conflicting DNS records.
- Follow Cloudflare's DNS and certificate instructions. Do not overwrite an existing record without investigating its owner and purpose.

## 10. Localized App Store listings

The app ships 20 languages, so the store listing does too. The copy lives in
`ios/docs/appstore/listings.json`, one entry per storefront language. Run this
from `ios/`:

```bash
node scripts/localization/check-listings.mjs --strict
```

That must pass before you paste anything into App Store Connect — it enforces
each field's character limit, keyword hygiene, and full coverage across all 20
languages. CI runs it on every push, so a failure here means something was
edited after the last green build.

**Ship the listings after the binary, not with it.** A storefront that promises
German while the approved binary still renders English is worse than an
untranslated listing, and the listing goes live the moment you save it while the
binary waits for review.

For each language, in App Store Connect → the app → **Localizations** → add the
language → paste the six fields from that language's entry.

- [ ] `name` is `TidyByte` in every storefront
- [ ] `subtitle` is within 30 characters in every language
- [ ] `keywords` has no space after commas and repeats nothing from that
      language's name or subtitle (Apple indexes all three together, so a repeat
      wastes a slot)
- [ ] `promotionalText` and `whatsNew` read as current copy, not a literal
      translation of the English
- [ ] Screenshots are still the English set — localized screenshots are a design
      task, tracked in `docs/APP_STORE_LISTING.md` §11, not part of this checklist
- [ ] If the Duo screenshot row is being uploaded: the single App Store Connect
      Duo group id is set (`TIDYBYTE_DUO_GROUP_ID`, or the `group` field on the
      `duo` family in `scripts/publish/plan.mjs`) — it cannot be read offline
      while the API key is empty, and `npm run publish:media -- --duo` throws
      until it is. Fallback only: if `npm run publish:verify` really shows **two**
      `APP_SCREENSHOT` groups for the Duo displays, set **both**
      `TIDYBYTE_DUO_OUTER_GROUP_ID` and `TIDYBYTE_DUO_INNER_GROUP_ID` (one
      directory each) instead; setting only one is not a split and fails loudly.
      See `docs/duo-readiness.md` §5
